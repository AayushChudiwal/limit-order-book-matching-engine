# Mutation testing: does the fuzzer actually catch bugs?

This is the evidence, not the claim. Every optimization commit in Phase 5
will be validated by the differential fuzzer and nothing else -- a fuzzer
that can't detect bugs produces the exact same green output as a correct
engine. This document exists so that claim doesn't have to be taken on
faith.

Generated by `fuzz_mutation_test` (`tools/fuzz_mutation_test.cpp`),
reproducible by running the binary directly -- no arguments, fully
deterministic given the seeds it iterates.

## Method

Seven deliberately broken engine variants (`BuggyOrderBook`, one runtime
`BugKind` each), each mirroring the reference engine's algorithm with
exactly one specific, realistic deviation injected at exactly one point
-- not seven independently-written copies that could drift from each
other or from the reference in unrelated ways. See
`include/lob/fuzz/buggy_order_book.hpp` for the full description of each.

For each bug, across 20 seeds, 20,000 generated ops per seed
(`DefaultProfile`, the PSX-derived mix):

1. Run `RunDifferential<OrderBook, BuggyOrderBookVariant<Kind>>` and
   record whether it caught the bug, and at what op index.
2. If caught, run `Shrink` (delta-debugging) on the failing sequence and
   record the shrunk size and how long shrinking took.

A `BugKind::None` baseline (no injected bug) is verified separately, in
the committed test suite, to match the reference engine exactly across
all three generator profiles -- this is what makes the other seven
results trustworthy. Without it, "caught!" could mean "the harness found
a bug" or could just as easily mean "`BuggyOrderBook`'s hand-mirrored
correct-path code has an unrelated implementation slip" -- there would be
no way to tell which.

## A real gap this process found, not a clean success story

`BestBidCacheNotInvalidated` went **uncaught across 5 seeds at 3000 ops
apiece** the first time this was run. Not because the injected bug was
wrong or too subtle -- `RunDifferential` compared `FullBook()` on both
sides (which reads the underlying price-level maps directly) but never
compared `BestBid()`/`BestAsk()` themselves. A stale best-price *cache*
is invisible to a check that never reads the cache. Fixed by adding an
explicit `BestBid()`/`BestAsk()` comparison to `RunDifferential`; after
the fix, the same bug is caught in 4 of 5 probe seeds within 30 ops and
the 5th within 610 (the numbers in the table above are post-fix, with a
larger 20-seed sweep).

This is kept in the record deliberately, in the commit history and here,
rather than quietly fixed and forgotten: it's the concrete demonstration
of why "verify the shrinker and harness actually work by testing them
against injected bugs" matters, rather than writing a harness, asserting
it should work, and moving on. A harness gap like this -- comparing
derived state but not a cached value that can independently go stale --
is exactly the class of thing that would otherwise surface for the first
time against Phase 5's real optimized engine, where a wrong-but-plausible
result is far more expensive to root-cause than a five-line fix caught
here.

## What this does and does not prove

**Proves:** the differential harness's comparison logic (fills, full book
state including per-order queue position, accept/reject outcomes, and
now best bid/ask) is sufficiently thorough to catch seven realistic,
independently-plausible matching-engine bugs, reliably, in a small number
of generated ops, with the shrinker reliably reducing any of them to a
handful of ops a human can read in seconds.

**Does not prove:** that the harness would catch bugs specific to a
*different* internal data structure than `BuggyOrderBook`'s (which still
uses `std::map`/`std::deque`, like the reference engine) -- a flat
price-array's tick-band boundary handling, a custom hash map's
collision behavior, or anything that manifests as memory corruption
rather than a wrong observable result. See `docs/phase5_readiness.md`
for an explicit, honest accounting of those gaps and what additional
guards Phase 5 needs.
